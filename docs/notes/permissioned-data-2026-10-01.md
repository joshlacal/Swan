# Permissioned-data alignment, 2026-10-01 (October 1 Spaces alpha)

Bluesky published the October 1, 2026 Spaces alpha (npm `0.0.0-spaces-alpha-20261001173819`, built from atproto `679724ad`). It renames several request and response fields, replaces the Spaces DPoP binding with HTTP Message Signatures, shortens credential lifetimes, adds credential revocation for repo hosts, and adds space revisions for write notifications. This note records the new immutable Swan profile, `permissioned-data-0016-2026-10-01`, which pins that release, and tracks which of those behaviors Swan already implements. The decisions made for this alignment are listed at the end of this note (Yellow, overridable before merge) for the workspace decision log, `Catbird+Petrel/docs/DECISIONS.md`; the previous alignment is [permissioned-data-2026-09-19.md](permissioned-data-2026-09-19.md) and the open-interop flag is described in [2026-10-01-spaces-open-interop.md](2026-10-01-spaces-open-interop.md).

## Lexicon delta from the 2026-09-19 pin

Six of the 30 Spaces lexicon files changed:

- `space/listSpaces`: query filter `type` is now `spaceType`.
- `simplespace/createSpace`: body field `type` is now `spaceType`.
- `space/notifyWrite`: `rev` is now `repoRev`; forwarded notifications add `spaceRev` and optional `prevSpaceRev`; declared errors `SpaceNotFound` and `FutureRev`.
- `space/listRepos`: entries are `{did, repoRev, hash, spaceRev}` in ascending `spaceRev` order; the cursor is an exclusive space-revision checkpoint and is omitted on an empty page.
- `space/getSpaceCredential`: descriptions only (HTTP Message Signature instead of DPoP; no `cnf.jkt`).
- `space/notifyCredentialRevoked` (new): `{space, credentials: [jti, …]}` sent by a space authority to repo hosts.

The profile lists 28 endpoints (27 plus `notifyCredentialRevoked`), and the `SwanSpacesWire` registry matches the lexicons' kinds, encodings, and declared errors.

## Intentional divergences recorded in the profile

The profile carries over the `getRepo` streaming divergence and both compatibility exceptions (the `@did-plc/server` submit status and the `listRepoOps` retention gap, both re-checked at `679724ad`). It rewrites the `notifyWrite` divergence for the new reference and adds the items listed in the open-interop note:

- `notifyWrite`: by default Swan requires a `req`-bound service JWT. Unbound tokens are accepted only with `--enable-spaces-open-interop`. An equal `repoRev` with a different `hash` is refused as equivocation (the reference ignores it), and forwards to registered syncers are queued durably and retried (the reference attempts each once from memory).
- `listRepos`: a cursor beginning with `did:` (Swan's pre-October-1 cursor) lists from the start instead of being compared as a string.
- `notifyCredentialRevoked`: by default Swan requires a `req`-bound service JWT, so a revocation shaped like the reference's (`iss`, `aud` and `lxm` only) is accepted only with `--enable-spaces-open-interop`. Revocations are retained for 3905 s instead of the reference's 3610 s, because Swan's verifier tolerates up to 300 s of expiry skew.
- `registerNotify`: by default Swan also requires `Atproto-Service-Auth`. Registrations made with the space credential alone are accepted only with the flag, and are rate-capped.
- `getSpaceCredential`: Swan's own authority issues 300 s credentials, not the reference's 600 s default. Both are under the 3600 s ceiling.
- `createSpace` / `updateSpace`: `managingAppPolicy` is rejected with `UnsupportedPolicy`.

## Implementation status

Done:

- Petrel re-pin. Wire members follow the renamed generated types: `notifyWrite` sends and accepts `repoRev`, and `listRepos` entries carry `repoRev` and `spaceRev`.
- The profile and registry above, set as the active default (`swan serve` / `swan verify --profile`).
- Request-field renames: `listSpaces?spaceType=` and `createSpace {spaceType}` in the handlers, the listing permission check, and Swan's own `createSpace` caller (`swan lab` space provisioning). The retired `type` key is rejected, not accepted as an alias.
- **HTTP Message Signatures (atproto#5569).** The Spaces-only DPoP validator is gone; ordinary OAuth DPoP is untouched. `getSpaceCredential` verifies the Bearer delegation, then an `atproto-space` signature over `("authorization")` whose required `keyid` is a P-256 `did:key`, and issues the credential with `cnf.kid` set to that key (no `aud`). Every credential-accepting route (`getRecord`, `listRecords`, `listBlobs`, `getBlob`, `getRepo`, `getLatestCommit`/`getRepoState`, `listRepoOps`, `listRepos`, `registerNotify`, `unregisterNotify`, `simplespace.getSpace`) takes `Authorization: Atproto-Space <credential>` plus `Atproto-Space-Audience` and verifies the signature over `("authorization" "atproto-space-audience")` against `cnf.kid`: 64-byte `r||s`, DER rejected, high-S accepted, optional `alg`/`keyid` checked, supplied parameters included in the signature base, other signature labels tolerated, duplicate `Authorization`/`Atproto-Space-Audience` rejected. The expected audience comes from the operation: the `repo` parameter for repo reads, the bare authority DID for space-host operations, matching the reference handlers. Failures render 401 `BadSpaceSignature` or `BadSpaceAudience`. Swan as a client (`SpaceCredentialBroker`, `InteropSpaceCredential`) generates a fresh P-256 key per credential and signs each request for its audience (`repo ?? spaceDid(space)`, the reference client's rule).
- **Credential revocation (atproto#5567).** Swan as a repo host receives `notifyCredentialRevoked`: service auth with `iss` = space authority, `aud` = the bare DID of an account Swan stores, `lxm` = the method, and (by default) a `req` body binding; unbound upstream tokens only under `--enable-spaces-open-interop`, as for the other notification receivers. Revocations persist in `control.sqlite` (new control schema migration v9, table `permissioned_space_credential_revocations`, keyed by a SHA-256 digest of `(space, jti)`), idempotently, for 3905 s from receipt (3600 + 5 + Swan's widest 300 s expiry skew; the reference uses 3610 s with its 5 s skew). Cleanup removes only rows past that deadline. Every credential presentation checks the list after its signature and before its audience, and a match is 401 `CredentialRevoked`; an unreadable list fails closed (503). Credential verification already enforced the 3600 s ceiling, finite integer `iat`/`exp`, `exp > iat`, a nonempty `jti`, and at most 5 s of future `iat`; Swan's authority still issues 300 s credentials. As a client, Swan surfaces `CredentialRevoked` as the terminal `InteropHTTPError.spaceCredentialRevoked` and has no retry loop for credential failures. The profile records the receiver's `req` default and retention as an intentional divergence.

- **Write notifications and space catch-up (atproto#5574).** As a space host, Swan now sequences writer updates. A `notifyWrite` from a repo host must come from the writer (`iss` = `repo`) and may address `<authority>#atproto_space_host` or the bare authority DID in both postures. The writer must pass the space's write policy. A `repoRev` equal to or older than the recorded one is ignored without a new revision or a forward, and one more than five minutes ahead is 400 `FutureRev`. An unknown or deleted space, or an authority this server does not host, is `SpaceNotFound` (previously a silent no-op for an unhosted authority). An accepted update stores the writer's `repoRev` and `hash` and allocates the next `spaceRev` in one transaction: the reference's `TID.nextStr(prev)`, i.e. the clock's TID or the previous revision plus one, so revisions strictly increase across all writers. The same transaction queues forwards to every registered service with `{space, repo, repoRev, hash, spaceRev, prevSpaceRev}` (`prevSpaceRev` omitted on the space's first update), signed by the authority for the registered service identifier, with a `req` that binds both revisions. The authority's own writes take the same path inside the commit transaction, so the later self-addressed outbox notification is ignored rather than double-forwarded. `listRepos` returns latest writer states in ascending `spaceRev` order; the cursor is an exclusive, unvalidated string checkpoint, every nonempty page returns its last `spaceRev`, and an empty page omits the cursor. As a repo host, Swan's existing durable outbox still notifies the authority after every local write, coalesced to the repo's latest state and retried with backoff until accepted or refused with a 4xx; under `--enable-spaces-open-interop` it now addresses `<authority>#atproto_space_host` even when it falls back to the authority's `#atproto_pds` endpoint. `registerNotify` and `unregisterNotify` are unchanged: space-host operations authorized by a space credential signed for the bare authority DID. Swan's only `listRepos` consumer (the `swan lab forum` thread syncer) reads the new shape and stops on the first empty page; it keeps no persisted checkpoint.

Nothing from the October 1 release remains open in this alignment.

## Compatibility boundaries

- Portable exports and operator account backups embed the profile ID and are accepted only under the same ID. Archives produced by a `2026-09-19` build do not restore on this build. Restore them with the build that produced them, or produce new ones after upgrading.
- A `notifyWrite` body that uses `rev` is rejected with 400 `InvalidRequest`. This applies both to a Swan peer still on the `2026-09-19` profile and to a reference repo host older than `679724ad`.
- A `listSpaces` query or `createSpace` body that uses `type` is rejected with 400 `InvalidRequest`. Swan rejects the key outright instead of ignoring it, so an old client fails loudly rather than receiving an unfiltered listing. The OAuth `space:` permission syntax is unchanged.
- Space credentials minted in the DPoP format (`cnf.jkt`), and any presentation under the `DPoP` or `Bearer` scheme, are refused. Holders reacquire a credential through a new delegation exchange with a fresh P-256 key. Ordinary OAuth DPoP sessions are unaffected.
- `listRepos` cursors issued before this build were writer DIDs. They cannot be reused as space revisions; such a cursor now lists the space from the start, which re-bootstraps the caller.
- A Swan peer still on the `2026-09-19` profile accepts only the bare authority DID as a hardened `notifyWrite` audience, so it refuses notifications this build routes through DID documents. It already refuses the renamed `repoRev` body, so this adds no new break.
- No stored data is migrated by the profile change itself. Control schema migration v9 only adds the empty revocation table; it does not touch existing rows.
- Account schema migration v24 (each account's `<did>.sqlite`) adds `space_rev` to `permissioned_space_writers` and `space_rev`/`prev_space_rev` to `permissioned_space_notification_fanout`, then backfills every writer row. Within each space, rows are taken in `(repoRev, did)` order; each gets its own `repoRev` as its `spaceRev` (what the reference's migration does) unless that would not be strictly greater than the previous row's, in which case it gets the previous value plus one. A `repoRev` beyond the five-minute `FutureRev` horizon at migration time is clamped to that horizon, so a stored far-future revision cannot exhaust the range. A unique `(space_uri, space_rev)` index then makes the exclusive page boundary lossless. The columns and backfill are re-checked on every open, so an operator re-running the older v21 writer-table rebuild cannot leave the column missing. Forwards that were queued before the migration have no space revision; they are dropped unsent, and subscribers recover through `listRepos`.
- Under `--enable-spaces-open-interop` any `did:plc`/`did:web` issuer can sign revocations for its own spaces, and the revocation table has one global cap (65,536 rows, each kept 3905 s). About 656 full 100-ID batches from throwaway authorities fill it; until rows age out, further revocations are refused with 503 and a revoked credential stays usable until its own expiry (at most 3600 s; Swan-issued credentials last 300 s). No per-authority quota was added because new DIDs are free. Without the flag, service-JWT keys resolve only from this server's own accounts and operator-pinned keys, so only those authorities can write to the table.
- Error names match the lexicons, but some HTTP statuses keep Swan's existing conventions: `SpaceNotFound` is 404 (the reference uses 400), and a refused writer or revocation issuer is 401 (the reference uses 403). A `getSpaceCredential` request with a duplicated `Authorization` field gets Swan's opaque `InvalidDelegationToken` (the reference reports `BadSpaceSignature`). The reference sender treats every one of these as a non-retryable 4xx, so delivery behaves the same.
- Clients must use HTTP Message Signatures for space credentials and `spaceType` for `listSpaces`/`createSpace`; both are covered above.
- The profile's SHA-256 is now `c86bdc739a1bb2a1e5666b5ff8c8d90eb0127ca5eb61ab059a416116c83c987e` (it changed with the `listRepos` and `notifyWrite` divergence text); `Scripts/verify-profile.sh` and `SwanInterop.expectedProfileSHA256` pin it.

## Decisions made while implementing (Yellow, overridable before merge)

- **Petrel pin.** Swan pins Petrel `f15887c9`, the head of Petrel bookmark `spaces-oct1-swan-20261002`, a sibling of the main Petrel October 1 line (`spaces-oct1-20261002`, `16dffa8d`). That ref must stay unmoved until this change merges, or be replaced by a durable ref and re-pinned; a re-pin also changes the profile's `petrelCommit` and therefore its SHA-256.
- **Profile.** Named `permissioned-data-0016-2026-10-01` after the release date. The generator pin stays `710ecb0a` because Swan's registry is hand-maintained and the generator code did not change.
- **Retired `type` key.** `listSpaces?type=` and a `createSpace` body with `type` are 400 `InvalidRequest`, alone or next to `spaceType`; there is no alias.
- **Inbound `notifyWrite` keys.** Exactly `{space, repo, repoRev, hash}`; the receiver requires `iss` = `repo`, so a forwarded notification is never accepted here.
- **Structured fields.** The RFC 8941 subset for HTTP Message Signatures is parsed in-tree (`SpaceHTTPMessageSignature.swift`) rather than through a new direct package dependency.
- **Credential cutover.** `cnf.jkt` credentials and credentials presented under `Bearer` or `DPoP` are refused outright; there is no dual-accept window. The exchange's signature failure is `BadSpaceSignature` (was `InvalidDPoPProof`).
- **Revocation receiver.** `req` is required by default (the profile divergence above). Retention is 3905 s. Storage is an unkeyed SHA-256 digest of `(space, jti)` in control migration v9, capped at 65,536 rows; when full, new revocations are refused with 503 so the authority can retry (see the open-interop bound under Compatibility boundaries). Any hosted account in any lifecycle state is a valid `aud`. Checks run signature, then revocation, then audience, and an unreadable list is 503.
- **Client audience.** `InteropSpaceCredential` signs for the request's `repo`, else the space authority's DID, and throws before sending a request that names neither. `CredentialRevoked` is terminal on JSON and streamed requests alike.
- **Old `listRepos` cursors.** A `did:` cursor lists from the start instead of returning an empty page (the profile divergence above).
- **Migration v24 backfill.** Each space's existing writer rows get their own `repoRev` as `spaceRev` when that is strictly increasing, else the previous value plus one, with far-future values clamped; a unique index enforces the order. The migration re-checks itself on every open.
- **Authority's own writes.** Sequenced inside the commit transaction, so the later self-addressed notification is ignored instead of forwarding twice.
- **Unhosted authority.** `notifyWrite` for an authority this server does not host is `SpaceNotFound` (previously a silent 200).
- **Forwards.** `spaceRev` comes from the reference's `TID.nextStr(prev)` rule, and the forward's `req` uses a new domain that binds both space revisions. Forwards queued before v24 have no space revision and are retired unsent.
- **Audiences on both `notifyWrite` hops.** The hardened receiver accepts the bare authority DID or `<authority>#atproto_space_host`; the open-federation sender always uses the latter, including on the `#atproto_pds` fallback.
- **Stricter behavior kept.** Equivocation (an equal `repoRev` with a different `hash`) is refused, and forwards stay in the durable leased queue.
