# Re-pinning Swan to the live permissioned-data branch — scope

Written 2026-08-14, prompted by a failed `bulleted.app` sign-in against
`swan.place`. Everything below is measured against the tree at `main` and
against `bluesky-social/atproto` as it stands today.

## 1. Where the branches are

| Branch | HEAD | Date | State |
|---|---|---|---|
| `permissioned-data` | `bddc99fb24c3` | 2026-08-13 | **active** — "fixes from review" |
| `permissioned-data-proposal-integration` | `3f6c96d5d2d2` | 2026-07-03 | **what Swan pins today** |
| `permissioned-data-lex-refactor` | `1af9f68fa03c` | 2026-06-16 | stale, superseded |

Swan pins the integration branch's HEAD. Against the active branch that is
**185 commits, 300 files, 62 lexicons** (55 modified, 5 added, 1 removed).
**30 of those lexicons are Swan's own surface** — `com.atproto.space/*` and
`com.atproto.simplespace/*`.

The branch moved yesterday. Anything built against it is aiming at a target
still in motion.

## 2. What actually broke the sign-in

Ground truth from the edge log (`/var/log/caddy/swan.place.log`), not from
Swan's own log, which records nothing for a successful request — verified with
a positive control:

```
08:01:14  GET /.well-known/atproto-did                200  bulleted/0.1.0
08:01:14  GET /.well-known/oauth-protected-resource   200  bulleted/0.1.0
08:01:14  GET /.well-known/oauth-authorization-server 200  bulleted/0.1.0
   … same three, twice more, at 08:01:26 and 08:03:48 …
```

Three attempts, all three documents fetched successfully, **no PAR attempted**.
Bulleted reads Swan's discovery documents and rejects their content before it
ever opens an authorization request.

Swan's authorization-server metadata is **not** malformed: it passes both the
pinned validator and the current branch's schema refinements. And the obvious
theory — that `scopes_supported: ["atproto"]` is too narrow — does not hold up
either: upstream advertises the same `atproto` plus three transitional hints,
with the comment *"other atproto scopes can't be enumerated as they are
dynamic."* Advertising more would not have helped.

What Bulleted requests, from `https://bulleted.app/oauth-client-metadata.json`:

```
atproto
include:app.bulleted.authFull
blob:image/*
include:app.bulleted.spaceAccess
space:app.bulleted.space?manage=create&manage=update&manage=delete&action=read_self
```

That last scope is **valid upstream and rejected by Swan three times over**.
Upstream's parser (`packages/oauth/oauth-scopes/src/scopes/space-permission.ts`)
declares `type` positional and required, `authority` optional defaulting to
`self`, `skey` optional defaulting to `*`, and `collection` / `action` /
`manage` all `multiple: true`. Swan's grammar
(`SwanCore.swift:198-243`) requires `authority` **and** `skey`, rejects
duplicate keys outright, and requires exactly one of `action`/`manage`.

`include:` and `blob:` do not exist in Swan at all.

Which specific precondition Bulleted checks is still unknown — its error text
is server-side, not in its client bundle, and all three of its fetches returned
200. That question is worth one message to the author; it does not change the
work below.

## 3. Is regeneration enough?

Partly. The typed wire surface **is** Petrel-generated —
`Sources/SwanSpacesWire/Generated/` carries "Generated by Petrel. DO NOT EDIT."
across 30 files. But four things sit outside that pipeline, and the one that
blocks sign-in is the furthest outside it.

### 3a. The generator needs a change, and its failure mode is silent

`format: "at-uri"` became `format: "space-ref"` — **28 occurrences** across the
space surface. `space-ref` is a new lexicon string format
(`packages/lexicon/src/validators/formats.ts:40-43`, backed by
`isSpaceRefString` in `@atproto/syntax`). The surface also picked up
`format: "tid"` (6 uses), which the pinned lexicons did not use here.

Petrel's `generator/type_converter.py:55-77` is an explicit format table ending
in:

```python
else:
    swift_type = "String"
```

So regeneration against the new lexicons **succeeds** and silently emits
`String` wherever a space reference used to be typed. No error, no warning —
just a weaker type than the code has today. `tid` is already mapped
(`:71-72`); `space-ref` is not. The Kotlin converter has the same table
(`generator/kotlin_type_converter.py:122`) and needs the same entry for parity.

**The cheap correct fix is one line per converter.** Upstream's `SpaceRef`
serialises as `at://{spaceDid}/space/{spaceType}/{skey}`
(`packages/syntax/src/aturi.ts:235-254`) and Swan's `SpaceURI` already produces
exactly that string (`SwanSpaces.swift:38-61`), as does its record form
(`:106`). So `space-ref` can map to `ATProtocolURI` and preserve today's typing
precisely. **No wire values change and no stored data migrates** — this is a
naming and typing change, not a format change. A dedicated `SpaceRef` type is
optional polish, not a prerequisite.

### 3b. Regeneration is checksum-gated

`Scripts/wire-generation-common.sh` pins the Petrel generator commit
(`c2a1cdbe`) and three SHA-256s — profile, Petrel manifest, generated output.
`Profiles/permissioned-data-0016-2026-07-30.json` carries 25 endpoints plus
`proposalCommit`, `referenceImplementationCommit`, `petrelGeneratorCommit`, and
the manifest digests. A re-pin means a **new profile document**, not an edit to
this one, and every digest re-derived. If the generator changes (3a), the
pinned generator commit moves too.

### 3c. Handlers — the part you expected

- `com.atproto.space.getSpace` is **removed**, replaced by
  `com.atproto.simplespace.getSpace`. Route registration, the 25-endpoint
  profile list, and `PermissionedData0016` (`SwanSpacesWire.swift:28`) all name
  it.
- Two new methods need handlers: `com.atproto.space.listBlobs` and
  `com.atproto.space.unregisterNotify`.
- New error names to map, e.g. `RepoNotFound` added to `getRecord` alongside
  the existing five.
- `com.atproto.simplespace.*` gained fields across nine files
  (`createSpace` +28/-17, `updateSpace` +24/-9, and so on).

### 3d. Not generated, not handlers — the actual blocker

1. **The OAuth scope grammar.** Hand-written in `SwanCore` and `SwanOAuth`;
   no lexicon describes it. Matching upstream means adopting the
   `oauth-scopes` model — positional `type`, defaulted `authority`/`skey`,
   repeatable `collection`/`action`/`manage` — and implementing the
   `include:` (permission sets, resolved from an NSID) and `blob:` families
   from nothing. Upstream ships seven permission kinds: account, blob,
   identity, include, repo, rpc, space. **This is what fixes sign-in.**
2. **`getSpaceCredential` now requires a DPoP proof** binding the credential
   to a key ("with the delegation token as the request's authorization token
   **and a DPoP proof signed by the key to bind the credential to**"). That is
   a behaviour change in the credential authority, not a type change.

## 4. Suggested sequencing

1. **Ask the Bulleted author** which precondition failed and which revision
   they target. One message, and it may collapse a lot of guesswork.
2. **Generator first** — add `space-ref` to both converters, mapped to
   `ATProtocolURI`. Small, independently testable, and it stops the silent
   `String` degradation before anything regenerates.
3. **Re-pin and regenerate** — new profile document, new digests, generator
   commit bumped. Diff the generated tree and expect it to be readable: same
   values, better names.
4. **Handlers** — the moved method, the two new ones, the new error names.
5. **Scopes** — the largest piece and the one that actually restores
   third-party sign-in. Worth its own design pass; the `include:` family in
   particular introduces a fetch-and-resolve step Swan has no equivalent of.
6. **`getSpaceCredential` DPoP binding.**

Steps 2-4 are mechanical and verifiable. Step 5 is a protocol feature, not a
port, and it is the one to schedule deliberately — especially against a branch
that moved yesterday.
