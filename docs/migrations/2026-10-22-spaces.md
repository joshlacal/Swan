# October 22 permissioned Spaces migration

This change updates Swan's native permissioned-data host and synchronizer to the October 22 wire contract. Space credentials now bind a client presentation key in the JSON exchange body; repository and record authenticity uses a dedicated account KEM key and response MAC; repository snapshots use STAR. It also supplies durable KEM publication work, preserves KEM material in account backups, and provides an offline whole-service backup that retains authority policy and queues. The governing workspace plan is [Spaces release readiness](/Users/joshlacalamito/Developer/Catbird+Petrel/docs/research/2026-10-23-spaces-release-readiness.md), especially sections 3, 5 and 9. The final integration handoff records the exact commits and executed checks; this document describes the implemented behavior and operator procedure.

## Wire and synchronization

`getSpaceCredential` accepts `space`, a P-256 `credentialKid`, and optional `delegationToken` and `clientAttestation`. No exchange Authorization header or HTTP signature is required. A request without delegation uses anonymous public-read policy; private policy remains hidden as `SpaceNotFound`. A supplied delegation must validate against its issuer and audience, bind the exact Space, and pass the durable replay fence. JWTs use the ordinary `#atproto` signing key and the authority's `#atproto_pds` service audience.

Resource presentations use `Authorization: Atproto-Space-Credential …` with the `atproto-space-credential` HTTP signature label and matching `tag`. The signature covers authorization and the expected Space audience. The old scheme is rejected. Structured Field byte strings accept standard padded and unpadded base64.

Credential reads of `getLatestCommit`, `listRepoOps`, `getRepo` and `getRecord` require `Atproto-Space-Want-Mac`. Owner OAuth reads may request it. The server computes the response MAC over the authenticated commit or record URI/CID, sets `Vary` for the request header, and exposes the response header through CORS. The KEM key is a separately wrapped account key; a signing key is never substituted.

`getRepo` streams a stable SQLite snapshot in STAR order, compares the accumulated LtHash with the committed root, and uses bounded file spooling. The commit body is stable for a repository state; the former per-reader IKM and commit signature are retired from this wire format. The native client creates a fresh ephemeral KEM share for every request, page and retry. OAuth DPoP nonce handling remains in force independently. A MAC failure triggers at most one fresh KEM lookup and retry. The native recovery path verifies the metadata MAC, record CID/body binding, ordering, duplicates, aggregate hash and fresh head witness before atomic publication. Incremental sync publishes only a complete authenticated terminal interval whose revisions and operations agree with the retained base. A valid nonterminal continuation, missing superseded record values, or a response beyond the durable batch budget selects bounded full-STAR recovery; the native client does not publish intermediate pages. Legacy CAR structures remain only for historical backup/recovery compatibility; they do not define the new `getRepo` response.

Native laboratory commands accept `SWAN_LAB_KEM_KEYS_FILE` (a JSON map from repository DID to its dedicated KEM `did:key`) or `SWAN_LAB_KEM_PUBLIC_KEY` for a single author. The map is re-read for every lookup and forced refresh. Current MAC/STAR commands do not require the legacy `SWAN_LAB_PERMISSIONED_COMMIT_KEY`; historical offline CAR verification retains its signing-key interface.

## Identity and KEM publication

New PLC account operations publish both `atproto` and `atproto_kem`. Rotation preserves other verification methods and retains the dedicated KEM key. Eligible existing accounts use a durable control-database lease: startup provisions missing KEM material, checks the current PLC operation and current PDS, then submits only the bounded KEM backfill operation. Failed attempts remain retryable, and interrupted submissions retain their operation journal. Accounts without publishable custody, including did:web accounts, are marked for manual publication. `swan account kem-method` emits the public verification method after operator authentication; it never exports the private key. The external account owner must publish that method and keep the private KEM material with the corresponding Swan account.

This is not authorization to modify production identities. First rehearse with disposable accounts and verify the exact current PDS and key custody. An already published third-party KEM key is not overwritten silently.

## Conversation Space authority

The optional `blue.catbird.labyrinth.conversation` policy is restricted to one explicitly configured local authority and the exact immutable UUID generation in each Space URI. Configuration requires the delivery service origin, service audience and pinned peer, local account key custody, and notification delivery. It is disabled by default. The delivery service must independently enable its issuer-readiness gate only after the deployed pair is qualified; a configured DID alone is insufficient.

Every credential issuance uses a short-lived standard authority service JWT to call `blue.catbird.labyrinth.getSpaceMembership`. The delivery service decides whether that DID is an accepted member with a current committed leaf for this exact active storage generation. Swan caches no affirmative result. An affirmative result permits registration of the Space in a durable authority registry, not a fabricated simple-space policy. Writer notifications perform the same live membership check for the repository DID, then atomically recheck the local active generation before accepting the writer hint.

Owner OAuth deletion proceeds in this order: persist local `deleting` intent and stable event ID; ask `blue.catbird.labyrinth.deleteSpaceGeneration` to atomically close that exact delivery-service generation; atomically mark local deletion terminal and enqueue the normal all-recipient deletion fanout; return success. The pending intent denies new credentials, writes and registrations during failures. A background service retries pending intents after restart with fresh 60-second service JWTs. Repeated remote deletion is idempotent. Local event identity and recipient leases remain durable. HTTP 408 and 429 retain retryable notification work.

Recipient reuse of an ordinary Space URI requires the explicit `adoptRecreatedRemoteSpace` operation: verified new credential, issue time after the retained deletion, exact deletion event compare-and-swap, complete stale staging purge and a monotonic generation floor. A delayed old import cannot publish into the recreated lifecycle. Conversation generations are immutable UUIDs and are never revived at the authority.

## Backup and restore

An account export is a content transfer, not a complete authority restore. New operator account backups include separately authenticated KEM material and bounded PLC operation history; supported v2 backup decoding remains available. Existing content-only restore rules intentionally leave authority policies and operational queues absent. Keep a historical backup's producing binary and configuration: an old backup is not evidence that a newer binary can recreate its operational authority.

For a full service restore, use `Scripts/service-snapshot.py`. The source data directory and all files must be owner-only. The service must be stopped; the tool checks open files, acquires the exclusive service-directory lease, locks every SQLite writer and copies each database with SQLite's backup API. It copies account key envelopes and blobs, authenticates the inventory with a separate 32-byte HMAC key, and publishes a destination atomically. It refuses symlinks, unsafe modes, modified inventories and an existing restore destination. The snapshot is not additionally encrypted; retain it on encrypted owner-controlled storage.

Keep the HMAC key outside the source and snapshot, and retain the original account wrapping key, OAuth/server/operator secrets, notification configuration, policy endpoint configuration, TLS material, the exact profile JSON files and producing executable separately. These external dependencies are deliberately not discovered or exported by the tool. Conversation authorities also depend on the delivery service database; its independent backup is outside this Swan snapshot.

Generate the snapshot integrity key once in a protected directory. It is **32 raw bytes**, unlike the base64 text key used by account backup commands. Retain it with the external recovery material; do not regenerate it before restoring an existing snapshot.

```sh
(umask 077; set -C; openssl rand 32 > /absolute/private/snapshot-hmac-key)

python3 Scripts/service-snapshot.py snapshot \
  --source /absolute/private/swan-data \
  --destination /absolute/private/snapshot-20261023 \
  --integrity-key-file /absolute/private/snapshot-hmac-key \
  --build-id "REPLACE_WITH_SAVED_EXECUTABLE_SHA256" \
  --profile-id permissioned-data-0016-2026-10-22

python3 Scripts/service-snapshot.py restore \
  --source /absolute/private/snapshot-20261023 \
  --destination /absolute/private/restored-data \
  --integrity-key-file /absolute/private/snapshot-hmac-key
```

Start the retained producing build against the new restored directory with the retained external secrets and configuration. Verify login, authority policy, members, authenticated reads, writer inventory, registration ownership, durable delivery retries and deletion state before switching any service. Upgrade the restored copy separately and repeat those checks. Do not replace or remove the original source directory.
