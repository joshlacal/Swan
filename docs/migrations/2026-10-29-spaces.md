# October 29 permissioned Spaces migration

This change moves Swan from the October 22 Spaces wire (`permissioned-data-0016-2026-10-22`, reference `ac0c9f15`) to the October 29 alpha (`permissioned-data-0016-2026-10-29`, reference `5d88b414a98de1ada22c94c78fa0667a7028163c`). The October 29 alpha retires `com.atproto.simplespace.*` and replaces its two independent read/write policies and app-access setting with one space policy of three kinds: personalspace, memberspace and managedspace. Swan is both a repository host and a space authority, so both halves change. The October 22 profile file is kept unchanged for historical verification; [the October 22 notes](2026-10-22-spaces.md) still describe the credential, MAC and STAR behaviour, which October 29 does not change.

## Wire changes

| Before (October 22) | After (October 29) |
| --- | --- |
| `com.atproto.simplespace.createSpace` with `readPolicy`, `writePolicy`, `appAccess` | `com.atproto.space.createSpace` with one required `policy` |
| `simplespace.updateSpace` patching each property | `space.updateSpace` replacing the policy wholesale |
| `simplespace.getSpace` for the owner or a space credential | `space.getSpace` for the owner's OAuth (`read_self`) only |
| `simplespace.deleteSpace` | `space.deleteSpace` |
| `simplespace.putMember` / `removeMember` / `listMembers` | `memberspace.putMember` / `removeMember` / `listMembers`, `PolicyMismatch` for other policies |
| `simplespace.checkUserAccess` (served, always `false`) | `managedspace.checkUserAccess` (served, always `false`) and a real outbound client |
| — | `space.removeWriter` |
| — | `space.clearRecords`, `importRepo`, `exportSpaceMeta`, `importSpaceMeta` (see below) |

The retired `simplespace` routes answer `404 Not Found`. All five Spaces namespaces, including the retired one, are on the XRPC proxy deny list, so a stale client never reaches an upstream PDS. `SpaceNotFound` is HTTP 400 on the lifecycle, member and credential routes, as in the reference. A user the policy does not admit is told `SpaceNotFound`; the user is checked before the app. A request naming another account's space still receives `SpaceNotFound`, not `NotSpaceOwner`, as Swan has always answered.

Writes into the published collections `com.atproto.space.policy` and `com.atproto.memberspace.member` through `createRecord`, `putRecord`, `deleteRecord` or `applyWrites` are refused with 400 `InvalidRequest`. Only the authority writes them, through the policy and member methods.

## Policies

- **personalspace**: only the authority reads and writes.
- **memberspace**: `publicRead`, `publicWrite`, `allowedApps` (attested OAuth client IDs; omitted admits any app; does not apply to writes), `publishPolicy`, `publishMembers`.
- **managedspace**: `managingApp` (a DID with an optional `#fragment`) and `publishPolicy`. Every user decision is deferred to the managing app.

Policies are normalized before storage: flags must be JSON booleans, `allowedApps` is sorted and de-duplicated, and an unknown `$type` is `UnsupportedPolicy`.

### Published records

When a policy sets `publishPolicy`, the authority writes its policy as `com.atproto.space.policy/self` into its own repository in the space. When a memberspace sets `publishMembers`, it writes one `com.atproto.memberspace.member` record per member, keyed by the member's DID. Swan's own owner row is never published. The records are reconciled in the same SQLite transaction as the policy or member change, through the ordinary authority write path, so they advance the authority's space revision and are announced with `notifyWrite`. Records already correct are not rewritten. Turning publication off withdraws them.

### Managed spaces

On a credential request (`access=read`, with the attested `clientId`) and on a write notification (`access=write`, without `clientId`) Swan asks the managing app's `com.atproto.managedspace.checkUserAccess`. It signs service auth as the space authority with `lxm=com.atproto.managedspace.checkUserAccess` and `aud` equal to `managingApp` as written. The endpoint is the named service of the app's DID document, or `#atproto_pds` for a bare DID. The request goes through the same outbound policy as other authority calls: DNS is validated, peers are pinned, redirects are refused, and the response is capped at 4 KiB with a 5 s timeout. Anything other than HTTP 200 with exactly `{"authorized": true}` denies. The check runs with no SQLite transaction open, then the decision is re-applied inside the transaction. No answer is cached. `serve` installs the client when the notification service resolver and the local space runtime are configured; otherwise every non-authority user of a managedspace is refused.

The October 22 stored managing-app decision table is no longer consulted. Its rows are cleared by the migration; the table and its storage API remain so older backups still decode.

### Writers

`removeWriter` drops one account from the space's writer set. `removeMember`, and `putMember` with `write: false`, also drop the member from the writer set. An account re-enters the set on its next authorized `notifyWrite`.

## Database migration (account schema v29)

Account databases migrate on first open. The migration adds `policy_type`, `publish_policy` and `publish_members` to `permissioned_simple_space_authorities` and converts each row:

1. If either side names a managing app, the space becomes a managedspace whose `managingApp` is `read_managing_app ?? write_managing_app`, as the reference `configToPolicy` does regardless of the policy columns. Its client allow-list and non-owner members are dropped. If that value is not a DID with an optional fragment, the space becomes a personalspace instead.
2. Otherwise it becomes a memberspace: `publicRead`/`publicWrite` from the public sides, `allowedApps` from an allow-list, members kept.

Every lossy conversion is written to `permissioned_space_policy_migration_v29` and logged on stderr, with one or more reasons: `one-sided-managing-app`, `different-managing-apps`, `managing-app-not-a-did`, `allow-list-dropped`, `members-dropped`. Stored managing-app decisions are deleted.

To see the effect before upgrading, or to read the record afterwards, run the read-only report against a copy of an account database:

```sh
swan account space-policy-report --data-directory /absolute/copy/of/swan-data --did did:plc:...
```

It opens the database read-only and never migrates it. Before v29 has run it prints the predicted conversions (`"recorded": false`); afterwards it prints the logged ones (`"recorded": true`). Do not point it at a production data directory from this branch; copy the database first.

## Profile and verification

`Profiles/permissioned-data-0016-2026-10-29.json` pins 33 endpoints, the reference archive SHA-256 `3e63e8f46acca4b879aca32aca9db7f0b9e8fe46556b0d4e5df2027d58b7757b`, and the lexicon and generated-wire manifests. `Scripts/verify-profile.sh` and `interop/fetch-reference.sh` now pin the October 29 tree. The profile records two new intentional divergences: Swan's `listMembers` includes the authority as a member, and a managedspace without a configured resolver refuses every non-authority user.

Because the profile ID changed, an October 22 backup restores only with its producing build, as with earlier profile changes. Keep that binary with the backup. Use `--profile-id permissioned-data-0016-2026-10-29` for new service snapshots.

## Not yet served

`clearRecords`, `importRepo`, `exportSpaceMeta` and `importSpaceMeta` are pinned in the profile and routed method-correctly, but answer 503 `permissioned_data_pending` until the second milestone of this migration lands.
